# macOS app and shared Rust core plan

27 September 2026. **Phase 0 baseline and native contracts recorded; no native app is implemented by this document.** The current web MVP and its pending hardware gates remain in effect.

## Recommendation

Build a SwiftUI macOS shell with an AppKit `NSTextView` editor, the existing Rust semantics compiled natively, and a Swift adapter for a user-selected Markdown folder. Keep CodeMirror on the web. Share document rules, Markdown transformations, file encoding, and eventually save-state decisions through `writer-core`; retain text input, undo, rendering, permissions, and physical storage in each platform.

The current core is ready for a native integration spike. It is not yet a complete document engine, a Swift package, or a safe folder-backed application. The largest risks are reproducing the editing experience and safely handling files modified outside the app, rather than compiling the parser for macOS.

Start with a working Swift-to-Rust call and a real editable text view before a broad extraction. Then move one proven behavior at a time, with the web consuming the same implementation. This prevents a speculative core that neither client actually uses.

## What to share

```text
                        writer-core
          Markdown • edits • focus rules • file codec
           document/save policy when both clients use it
                         /          \
               writer-wasm          writer-ffi (new)
                    |                    |
             Svelte + CodeMirror    SwiftUI + NSTextView
                    |                    |
             IndexedDB adapter      Swift file adapter
                                    selected folder + recovery
```

**Keep in Rust:** parser semantics, permitted preview markup/URLs, source ranges, formatting edits, sentence boundary rules, encoding metadata and transformations. Later add portable document identity/revision rules, save/conflict decisions, tag normalization and search semantics where two clients justify them.

**Keep in the platform adapters:** CodeMirror/TextKit text storage, selection, marked text/IME, undo stacks, input events, visual spans, caret drawing, scrolling, menus, accessibility, background scheduling, filesystem grants, file observation, IndexedDB transactions, file coordination, and actual writes. Rust should not become a second live text buffer or a custom cross-platform undo engine.

**Share as resources when useful:** Markdown fixtures, expected semantic output, preview stylesheet, command identifiers, font assets and license notices, and design token values. Initially document Swift colors and typography against the CSS defaults; do not put theme controls or a design-token generator in Rust merely to increase shared code.

An example future feature: task-list semantics and a toggle edit belong in Rust; a web click handler and a Mac menu action apply the same edit. A new toolbar or Finder action is platform-specific. A common engine reduces semantic drift but does not automatically provide both interfaces.

## Native implementation choices

Use SwiftUI for windows, toolbar, preferences, and an optional folder browser. Use `NSViewRepresentable` to host a long-lived `NSTextView`; prototype TextKit 2 and its decoration behavior before committing to a custom rendering approach. SwiftUI supports this AppKit integration directly. Avoid rebinding/replacing the complete editor string on each SwiftUI update because selection, undo, and composition must remain stable. This is an engineering recommendation, not a measured performance advantage. [Apple integration documentation](https://developer.apple.com/documentation/swiftui/nsviewrepresentable).

Prefer a dedicated `writer-ffi` crate using UniFFI and a local Swift package containing generated bindings and the native library. Keep UniFFI dependencies outside `writer-core` and `writer-wasm`. Existing `usize`, borrowed strings, and string-valued span kinds need deliberate owned, checked binding records. Preserve the existing web JSON contract during migration. UniFFI generates Swift support, but packaging and build integration are still our responsibility; its current guide also flags Swift 6 concurrency limitations. Begin with synchronous, pure functions called on a serial background executor, returning results to the main actor; verify generated code against the installed compiler. Pin a UniFFI version compatible with Rust 1.87 or make a separately tested toolchain upgrade. [UniFFI Swift guide](https://mozilla.github.io/uniffi-rs/latest/swift/overview.html), [UniFFI overview](https://mozilla.github.io/uniffi-rs/latest/).

Keep UTF-16 as the shared range convention: it matches CodeMirror and AppKit's `NSRange` conventions. Never substitute Swift `String.count` for UTF-16 length. Validate bounds, surrogate pairs, and non-BMP selections at the bridge; test grapheme clusters in the editor. Carry document identity and revision alongside asynchronous results and reject stale results after edits or document switches. Defer decoration updates during marked-text composition. Apply formatting as one native undoable edit.

The workspace release profile currently uses `panic = "abort"`. Define recoverable binding errors explicitly and do not claim UniFFI will catch every Rust panic; an unexpected abort can terminate the app. Keep unsaved-content recovery independent of successful analysis. Profile full-text copies and full-document analysis before considering incremental parsing.

Reuse Rust-generated preview HTML inside a read-only `WKWebView` with bundled CSS for the initial Read/Split implementation. Disable document scripting and automatic remote loads, intercept navigation, and preserve Rust's image placeholders. This reuses the preview presentation without introducing a second Markdown parser. A fully native reading renderer is optional later work.

Match neutral opaque paper, iA Writer Mono, the cyan caret, visible muted Markdown markers, sentence focus, and the quiet save label. Obtain the matching desktop font files and retain license notices; the repository currently bundles WOFF2 webfonts. Use native controls and availability-gated Liquid Glass for lightweight chrome, with readable fallbacks. [Apple Liquid Glass guidance](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass).

## Folder and durability contract to settle before implementation

Recommended first release: one selected folder, a flat list of Markdown files, one editable document at a time, optional collapsed navigation, and a recoverable untitled draft before folder selection. Reopen the last draft directly. File selection is an action, not mandatory onboarding. Defer recursive browsing, attachments, deletion, multiple editing windows, linked tags, and synchronization.

1. Swift presents a folder picker and persists a security-scoped bookmark. For the recommended sandboxed build, configure user-selected read/write access and balance security-scoped access calls; handle stale bookmarks and revoked/missing access without discarding text. A website-distributed app can use App Sandbox; it is distinct from Hardened Runtime. [Apple sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).
2. The selected folder contains ordinary `.md` files. Autosave writes the actual chosen file, not a download copy. Existing `.markdown`/`.txt` import compatibility can remain; new documents use `.md`. Never rewrite an untouched file just by opening it. Define how mixed line endings, UTF-8 BOM, and unsupported encodings behave before enabling writes.
3. Track editor revision separately from the last observed disk version. Use a content fingerprint and useful file identity metadata; timestamps alone are insufficient. Keep identity/URLs/bookmarks outside Markdown text. Specify how reopen and rename update the local catalog; duplicate files must not accidentally share identity.
4. Serialize writes per file, keep newer edits pending, and commit through a temporary sibling plus coordinated replacement. Preserve required file attributes and clean up abandoned temporary files. File coordination and atomic replacement address different problems: neither alone detects every noncooperating external writer. Validate disk content before writing and preserve recovery content so the app can surface races rather than promise universal cross-process compare-and-swap.
5. Observe external modifications, moves, and deletion through native file presentation/observation. Reload a clean buffer when safe; if local edits exist, pause overwriting and offer reload, save a copy, or an explicit overwrite after preserving versions. A deleted file must not be silently recreated. Apple provides `NSFileCoordinator` and `NSFilePresenter` for participating processes. [Coordinator documentation](https://developer.apple.com/documentation/foundation/nsfilecoordinator), [Presenter documentation](https://developer.apple.com/documentation/foundation/nsfilepresenter).
6. Store bounded recovery copies and untitled drafts in Application Support, separate from the selected folder and any rebuildable index. Record what survived a successful commit; recover interrupted sessions; prune only after newer copies are durable. A missing folder, full disk, denied permission, or write failure must keep the buffer recoverable and Save a Copy available.
7. The delayed saved label is presentation only. Open, New, folder switch, close, quit, and update must inspect the real committed revision/error state. Define save and recovery failure states separately; never report a disk file saved because only a recovery copy was written.
8. Reject path traversal and handle case-insensitive filename collisions, Unicode names, symlinks, and rename collisions deliberately. Begin with regular files inside the chosen folder; do not follow links outside the grant. Test filenames with accents and emoji.

Rust can decide whether a document is dirty, whether a completion is stale, and what a conflict means. Swift still has to prove and execute the physical commit. IndexedDB can check a revision within a transaction; arbitrary filesystem writes have different guarantees. Do not hide that difference behind a falsely identical storage interface.

## Phase 0 decisions and baseline

These are implementation contracts for the private Mac prototype and first folder-writing build. They are not claims that the native client or its storage tests exist.

| Area | Decision | Validation still required |
| --- | --- | --- |
| Release slice | macOS 14 or later, Apple silicon (`aarch64-apple-darwin`) for the private prototype. One window, one selected folder, flat `.md` list, one editable file, and an untitled recoverable draft before selection. Folder choice is optional at launch. | Confirm Intel demand before promising a universal build; test on the oldest supported macOS. |
| Folder grant | Sandboxed user-selected read/write folder with a persisted security-scoped bookmark. Re-resolve on launch and ask for renewed access when stale or revoked. The editor and Application Support recovery remain available while access is missing. | Bookmark relaunch, moved folder, revoked grant, and app replacement. |
| File boundaries | Open regular `.md` files directly within the grant. Import `.markdown` and `.txt` as copies; create `.md`. Do not follow symlinks outside the folder. Reject traversal, reserved/path separator names, and case-insensitive or Unicode-normalization collisions before creation or rename. | Accents, emoji, case/normalization collisions, symlinks, and rename races. |
| Encoding | Accept valid UTF-8, with or without BOM. Preserve a pure LF or CRLF convention and BOM on native writes. Opening alone never rewrites bytes. Mixed endings require an exact-preserving codec before native autosave is enabled for such a file; until then, open it read-only with Save a Copy or an explicit conversion choice. The existing web import/export behavior remains: any CRLF selects CRLF on export. | Specify and test per-break preservation in phase 2.1, then lift the native mixed-file restriction; reject invalid UTF-8 without replacing the live draft. |
| Identity | Assign each opened file a local UUID in the Application Support catalog, separate from Markdown. Reconcile by file resource identifier when available, canonical URL within the grant, and content fingerprint; never treat a matching filename or fingerprint alone as identity. A copy gets a new UUID; ambiguous rename/move matches require user resolution. | Relaunch, external rename, duplicate content, replacement inode, and catalog rebuild. |
| Revision and disk baseline | Increment an editor revision for edits. Record the last committed revision and a disk fingerprint (content hash plus useful file identity metadata) at open and after every successful write. A completion for another document or an older revision cannot mark the current buffer saved. Re-read and compare disk content immediately before replacement; keep recovery data through uncertain races. | External cooperating and noncooperating writers, stale completion, and write interleavings in phases 3–4. |
| Recovery | Keep untitled drafts and bounded versioned copies in Application Support, outside the selected folder. Write a recovery copy before a risky replacement and after edits on a bounded schedule. Prune only after a newer recovery copy or disk commit is durable. A recovery commit is labeled `Recovered locally`, never `Saved to file`. | Crash points, failed recovery writes, capacity bounds, and pruning in phase 4. |
| Conflict and failure | On external edit with a clean buffer, reload and keep selection where possible. With local changes, stop writes and offer Reload, Save a Copy, or explicit Overwrite after preserving both versions. Deletion and permission loss also stop writes; deletion never silently recreates the file. Full disk, coordination, bookmark, and recovery failures keep live text and Save a Copy available, with an immediate persistent error. Close, switch, quit, and update check the committed revision and error state. | Fault injection and UI checks in phase 4. The file system cannot promise universal compare-and-swap against noncooperating writers. |
| Command fallback | Editor creation, typing, undo, local recovery, and Save a Copy do not wait for Rust analysis. While analysis is loading or failed, keep the last safe styling or show plain text; disable Rust-dependent formatting commands and show a retryable status. Native menu/help exposes only executable commands. File, find, and view actions stay in the platform adapter. Once the bridge is ready, use Rust edits as one undoable transaction; reject invalid UTF-16 ranges. | Browser degraded-startup and Mac bridge checks before phase 2.3 removes any local formatting path. |

The extraction inventory is `apps/web/src/files.ts` (pure UTF-8/BOM/newline policy only), `apps/web/src/focus.ts` (sentence scanning and fallback block policy; CodeMirror change mapping stays local), local formatting wrappers and provisional count logic in `editor.ts`/`App.svelte` (route through existing Rust commands/counts after fallback is proven), then pure save-state decisions in `App.svelte` (after the native one-file save contract is exercised). Browser file picking/download, CodeMirror transactions, IndexedDB transactions, actual Swift file writes, geometry, and presentation stay in adapters. No extraction occurred in phase 0.

Before the first extraction, Vitest now fixes the current file codec behavior for BOM/CRLF, LF Unicode, mixed endings, invalid UTF-8, extension and size limits; it also fixes focus behavior for adjacent sentences, wrapped/soft lines, headings/blank lines, punctuation/quotes, decimals, emoji/UTF-16 positions, and mapped ranges after typing. The production-preview Playwright migration suite checks imported bytes through export, rejected invalid UTF-8 without draft replacement, and focus/undo through the actual editor and WASM build on a separate port. Existing Rust tests cover Unicode ranges, preview restrictions, tags, and command edits. Add command selection/undo and unavailable-WASM UI cases before phase 2.3, and save interleaving/conflict UI cases before phase 3. Define native codec, bridge, and filesystem cases alongside the consuming phase, as [web-regression-plan.md](web-regression-plan.md) requires.

Phase 0 verification on this working tree: `cargo test -p writer-core` (11 passed), `npm run check` (zero errors/warnings), `npm test` (12 passed), `npm run build` (passed), and `npx playwright test -c playwright.migration.config.ts` (four passed in isolated headless Chrome, including 1280px and 390px focus runs). These are automated checks, not Safari, hardware, native build, or file-fault measurements.

## Phased implementation

Each numbered subtask is intended as a separate, reviewable agent run. The larger phases are milestones, not single prompts. No phase should leave the web on a second untested semantic implementation.

**First step: migration tests.** Identify the code to extract into Rust and write focused tests for all of that code at the library/function level and through the affected web UI before moving it. Preserve those expectations after extraction and add Swift integration checks as the Mac app consumes the library. Define the concrete tests with each extraction; develop the full testing strategy incrementally. A comprehensive testing project is not a prerequisite. See [migration testing scope](web-regression-plan.md).

## How to use Luna and Sol

Use Luna for bounded changes once the interface, fixture, and acceptance gate are settled. Use Sol for the initial build/FFI work and again for TextKit lifecycle, persistence races, and release configuration. Restricting Sol to scaffolding alone would leave the most consequential design decisions to later implementation prompts.

This allocation is an engineering judgment, not a measured result for this repository. It fits OpenAI's positioning of Luna for efficient repeatable work and Sol for demanding reasoning; evaluate their patches against the same gates. [Official OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model).

Suggested prompt for each subtask:

> Implement only task [number] from docs/macOS-plan.md. Read AGENTS.md and the relevant design/architecture decisions first. Preserve existing uncommitted work. Keep Markdown semantics in writer-core and platform I/O/input in the adapters. Add tests for the named behavior and failure modes, run the relevant checks, and update the decision documents with implemented behavior and measured results. Do not start the next task. Report the changes, evidence, and remaining gate. If the task requires changing the agreed ownership or durability contract, describe the precise issue before broadening the implementation.

## Benefits and costs

The main benefit is direct ownership of ordinary files: people choose a folder, edits reach those Markdown files, and other editors, Git, or their existing backup tools can use them. Finder integration, native menus, keyboard behavior, and installed-app availability are further benefits. Rust semantics can be fixed once and exercised by both clients.

The app can operate offline from installation and store recovery outside browser storage. It still needs explicit recovery behavior: ordinary files can be deleted, disks can fail, and a native app is not itself a backup. Selecting an iCloud/Dropbox-managed folder delegates synchronization to that provider; it does not make the web app share those files or solve concurrent cloud edits. Provider folders require separate testing before support claims.

Costs are a second editor/UI implementation, two integration test surfaces, Rust-to-Swift packaging, native file races, signing, distribution, and app updates. Lower memory, faster typing, and lower battery use are hypotheses to measure. There is no credible code-reuse percentage yet; share semantic behavior rather than targeting a percentage.

A Swift shell around the existing web editor in `WKWebView` would preserve more UI immediately and is a reasonable fallback if speed to first download dominates. It still requires a native file bridge and the same durability work. The recommended native editor path better serves the stated Swift/macOS direction, at the cost of recreating and validating text interactions.

## Direct distribution

A Mac App Store listing is not required to offer a Mac app on a website. For a normal Gatekeeper-compatible release, plan Apple Developer Program/Developer ID credentials, signing with Hardened Runtime, notarization, ticket stapling, and a DMG or ZIP. Notarization is separate from App Store review. [Apple distribution overview](https://developer.apple.com/documentation/technologyoverviews/distribution), [Developer ID](https://developer.apple.com/developer-id/), [notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [packaging formats](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

Manual website downloads are enough for V1 updates. Automatic updating is a separate later feature with its own signing and rollback design. Native application-support data and the selected Markdown folder must survive replacing the `.app` bundle. No installer should place user documents inside the app bundle.
